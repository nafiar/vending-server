# Architecture

This is the rulebook this repository is held to. It is short on purpose: every
rule in it is either enforced by a test or visible in the package layout, and a
rule that is neither does not belong here.

The shape is clean architecture, adapted to one Go service with a relational
database and a locking story that matters. The vocabulary is `model`, `common`,
`repository`, `usecase`, `delivery`, and those are also the directories.

```
cmd/vending-server/   flags, subcommands, the process
internal/
├── model/            domain types, the business error, pure rules. Imports nothing internal.
├── common/           config, logging, security, the clock, calendar and paging. May import model.
├── repository/       one port per table or external thing, plus its driver(s) in a subpackage.
├── usecase/          the business rules, one package per story.
├── delivery/         inbound adapters: http/ (requests) and scheduler/ (the clock).
└── app/              the composition root: where the drivers are chosen.
web/                  the admin web, embedded
test/api/             black-box end-to-end tests over real MySQL
```

---

## 1. Imports point inward

The only rule that matters, and the one everything else follows from:

```
delivery ──▶ usecase ──▶ repository (port) ──▶ model
     │            │              │                ▲
     └────────────┴──────────────┴── common ──────┘
```

- `model` imports nothing from `internal/`. That is what lets every layer share
  its types without importing each other.
- `common` may import `model` and nothing else internal.
- A `repository` port may import `model` and `common`, never a usecase or
  delivery.
- A `usecase` may import `model`, `common` and repository **ports**, never an
  adapter, and never `delivery`.
- `delivery` may import `model`, `common` and usecase **ports**, never a
  repository.
- Nothing imports `app` except `cmd` and the end-to-end tests, which build the
  graph with the same function the binary does (§7).

This is enforced, not asked for: `internal/architecture_test.go` reads the
imports of every non-test file under `internal/` and fails the build on a
violation. An arrow drawn in a document is a suggestion; a test is a rule.

## 2. Ports and adapters

A port is an interface in a package named after the thing it stands for. Its
drivers live in subpackages of it, one per technology:

```
repository/machine/machine.go     the port:   machine.Repository
repository/machine/mysql/         the driver: mysql.MySQL, with var _ machine.Repository = (*MySQL)(nil)
repository/machine/mock/          the mock:   generated by mockgen
```

A usecase imports `repository/machine`, never `repository/machine/mysql`. The
architecture test checks the import path's depth to catch exactly that, which is
why the layout has to be port-at-the-top and driver-in-a-subpackage.

Every port carries `//go:generate mockgen`, and `make generate` regenerates all
of them. A port with no mock is a port that will be tested against a database.

**Read ports are separate from write ports** where the write side has an
invariant worth protecting. `audit.Repository` is write-only, because the one
rule about the change log is that a row commits with the change it records; the
change-log screen gets `audit.Reader` instead. Same for
`transaction.History` and `restock.History`. One driver struct usually
satisfies both, bound to a transaction for the write and to the pool for the
read — but a reader is never handed the methods that write.

**Ports are defined by what the business needs, not by what SQL can do.** A
repository method is allowed to be a query that sums or joins, and
`repository/report` is nothing else: asking the database for "revenue per
machine this month" is right, because the alternative is moving a year of
transactions into Go to add them up. What a repository may not do is decide
something. `report.RevenueByLocalDay` returns days, and which days belong to
which week is worked out in `usecase/recap`, because a week starting on Monday
is one idea and it lives in `common/calendar`.

## 3. The unit of work

Several stories have to change more than one table atomically: a purchase
touches the slot and the transactions; an operator's visit writes the session,
its lines, every slot and the machine's catalog version; every admin change
writes its change-log row. The transaction is therefore a port of its own.

```go
err := uc.uow.Do(ctx, func(tx uow.Tx) error {
    m, err := tx.Machines().LockShared(ctx, machineID)   // 1. machine
    s, err := tx.Slots().LockForUpdate(ctx, m.ID, n)     // 2. slot
    open, err := tx.Transactions().CountOpenShared(ctx, s.ID)
    ...
    return tx.Audit().Write(ctx, model.AuditEntry{...})  // same unit of work
})
```

Four things about it:

- **`uow.Tx` is a bundle of the same ports**, each bound to this transaction, so
  everything written through them commits together or not at all. A usecase
  never sees `*sql.Tx` — it must not import `database/sql` at all (§4).
- **Locking is part of the port's contract**, spelled out in the method name:
  `LockShared`, `LockForUpdate`, `CountOpenShared`. A method with no lock in its
  name takes none, and says so in its doc comment. This is the only way a
  reviewer can check a lock story without reading the SQL.
- **The lock order is machine, then slot, then transaction**, everywhere,
  without exception. It is the only defence against deadlock between
  purchases, dispense results and restock visits.
- **The retry lives in the driver** (`mysqldb.Runner`), not in a rule: InnoDB
  deadlocks and lock timeouts are retried there. A business rule that knows
  about deadlocks is a business rule written around its database. The one thing
  it asks of a caller: because `fn` may run twice, it must not carry state over
  from a failed attempt — assign to variables the caller declared, and reset
  them at the top of `fn` rather than appending to them.
- **`uow.Read` is the read-only twin**, for a story that asks several questions
  that have to agree with each other: every statement inside it sees one
  snapshot. A single read needs neither, and goes to a pool-bound repository.

`uow.Tx` grows as the system does. If it ever gets wide enough that a usecase
depends on far more than it uses, the next step is for each usecase to declare
the narrow subset it needs; one driver bundle satisfies them all structurally,
with no change to the port.

## 4. What each layer may do

**`model`** is types, constants, and pure functions over them: `model.Changes`,
`model.Tally`, `model.IsFinal`. No I/O, no clock, no internal imports, no wire
tags. If a rule can be stated as a function of its arguments, it goes here,
where it can be tested with a table.

**`common`** is the shared machinery a rule may use: `config`, `logx`,
`security`, `clock`, `calendar`, `imagex`, `paging`. The test for whether
something belongs here is that more than one layer needs it and it decides
nothing about any one story. `calendar` is here because six callers do date
arithmetic; `paging` because two screens clamp a page the same way.

**`repository`** holds the ports and their drivers. A driver may build SQL,
scan rows and map a driver error to a sentinel (`model.ErrNoRecord`,
`model.ErrDuplicateID`). It must not write a message for a screen: wording
belongs with the rule that failed, so the same missing row can be "Transaksi
tidak ditemukan." in one story and "Slot tidak ditemukan." in another.

**`usecase`** is where the decisions are. One package per story, each with a
`UseCase` interface, a `Service` implementing it, and `var _ UseCase =
(*Service)(nil)`. A usecase may not import `net/http` — a rule that knows about
requests cannot be reused by the command line — and may not import
`database/sql`, because that is the port's job to hide. Both are enforced.

**`delivery`** is inbound adapters. `delivery/http` decodes a request, calls one
usecase, and maps the result to a wire shape; `delivery/scheduler` does the same
for the passing of time. Two things belong to this layer and to no other:
turning a business error code into an HTTP status (§5) and turning a domain
value into JSON field names (§6). No rule is decided here. A handler holds
usecase ports only — no pool, no service struct — which is what makes it
testable with mocks and `httptest`.

## 5. Errors

A failure a caller should see is a `*model.Error`: a code, a message in Bahasa
Indonesia (the screens show it as it is), optional per-field messages, and
optional extra fields merged into the JSON body.

```go
return model.NotFound("Slot tidak ditemukan.")
return model.FieldErrors{"price": "Harga harus lebih dari 0."}.Err()
```

**No layer below delivery decides an HTTP status.** `model.Error` has no
`Status` field; `delivery/http/status.go` maps a code to a status in one table,
and that table has a test. A new code that nobody adds to the table shows up as
a failing test rather than as a silent 500.

Anything that is **not** a `*model.Error` is a server fault: it is logged with
the request id and reported as `INTERNAL`, never passed through to the caller.

Repositories return sentinels, not messages. `errors.Is(err,
model.ErrNoRecord)` is how a usecase recognises "there was no such row" and
chooses what to say about it.

## 6. Wire shapes

Every JSON field name the admin web or the Kiosk Agent reads is declared in
`delivery/http/dto_*.go`, next to the mapper that fills it. Nothing below
delivery carries a struct tag.

The field names are a contract with two clients that are deployed separately, so
they are guarded twice: `test/api/testdata/contract.golden` records the shape of
every response of every route and is compared byte for byte, and the end-to-end
tests declare their own structs rather than importing the server's — a test that
decodes into the server's types cannot notice a field being renamed, because it
gets renamed on both sides at once.

Regenerate the golden file deliberately, and read the diff:

```bash
make contract VENDING_TEST_DSN='…'   # go test ./test/api -run TestAPIContract -update
```

## 7. Composition and testing

`internal/app` is the composition root. It is the only package **above the
repository layer** that names a concrete driver (`mysql`, `local`), and it
exists as a package rather than a file in `cmd` so that the end-to-end tests
build the graph with the same function the binary does. Wiring a test
differently from production is how a test suite starts proving the wrong thing.

The one other place a driver names a driver is `repository/uow/mysql`, and it
has to: the bundle it hands out is the per-table mysql repositories bound to one
`*sql.Tx`, so building them is its whole job. It is a driver composing drivers
of the same technology, which is the opposite of a rule reaching for one.

Everything below receives its dependencies as interfaces, which is what the
test layers rest on:

| Layer | Tested with | What it proves |
| --- | --- | --- |
| `model`, `common` | table tests, no fakes | the pure rules: the tally, the changed fields, the calendar, the page clamps |
| `usecase` | mock repositories (`gomock`) | the orchestration **and the lock order**, which a mock can assert and a database cannot |
| `repository/*/mysql` | the end-to-end suite | the SQL, against a real MySQL |
| `delivery/http` | mock usecases + `httptest` | status codes, access rules, JSON field names |
| whole system | `test/api` over real MySQL | the PRD's test cases, on a fake clock, each test in its own database |

Two of those deserve their own note:

- **The concurrency gate.** `TestConcurrentPurchasesNeverOversell` fires twelve
  purchases at a slot holding three and must pass under `-race -count=5`. It is
  the only test that can catch a lost lock, and a lost lock is the worst failure
  this system has: it sells an item that is not there and nothing looks wrong
  afterwards.
- **The integration tests skip silently without a DSN.** `go test ./...` with no
  `VENDING_TEST_DSN` runs the unit tests and skips all thirty end-to-end ones,
  which looks identical to passing. CI must set it, and so must anyone judging
  whether a change is green.

```bash
go test ./...                                                             # unit tests only
VENDING_TEST_DSN='root:secret@tcp(127.0.0.1:3306)/' go test -race ./...   # everything
make generate                                                             # regenerate the port mocks
```

## Adding a story

1. Types it needs → `model`.
2. Data it needs → a `repository` port, plus a `mysql` driver and
   `//go:generate mockgen`. Put the read behind its own interface if the write
   side has an invariant to protect.
3. The rules → a `usecase` package with a `UseCase` interface, tested against
   mock repositories. If it writes more than one table, do it inside `uow.Do`,
   in the lock order, with the audit write in the same unit of work.
4. The route → a handler in `delivery/http`, its wire shape in `dto_*.go`, its
   access wrapper in `router.go`, and a handler test with mock usecases.
5. Wire it in `internal/app`.
6. Run the full gate with a DSN, and regenerate `contract.golden` only if the
   contract was meant to change.
